# AI + Geo Foundation (pgvector / PostGIS) — Design Note

**Status: forward-looking. Nothing here is implemented yet.** This note records how we
*would* add semantic matching (pgvector) and proper radius search (PostGIS) on top of
the PostgreSQL backend, and confirms each step is reversible. Do not action without a
dedicated task.

---

## 1. Extension availability & how to enable

Because Railway runs Postgres in a container you control, there are **no
platform-level restrictions** on extensions — but the *stock* Railway Postgres image
does not ship every extension preinstalled. Options, easiest first:

| Path | pgvector | PostGIS | Notes |
|---|---|---|---|
| **Railway "pgvector" template** | ✅ preinstalled | ❌ | Fastest if we only need embeddings. |
| **Railway "Supabase Postgres" template** | ✅ | ✅ | Production image with 50+ extensions (PostGIS + pgvector). Recommended if we want both. |
| **Custom Docker image** (e.g. `pgvector/pgvector` or the community `postgis+pgvector` image) | ✅ | ✅ | Full control; pin the image in the Railway service. |
| Stock Railway Postgres | ⚠️ may need install | ❌ | Verify with `SELECT * FROM pg_available_extensions WHERE name IN ('vector','postgis');` before relying on it. |

Enabling, once the image provides the binaries (run once per database):
```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS postgis;
```

**Local dev (this machine, PostgreSQL 17):** `vector 0.8.2` is already available, as are
`cube` and `earthdistance` (a lighter geo option). **PostGIS is NOT installed locally** —
it would need the PostGIS bundle added to the local install, or use the Supabase/custom
image via Docker for local parity. So pgvector can be developed locally today; PostGIS
work needs an image/install change first.

> Migrating to a different Postgres image on Railway is a service-settings change; data
> persists in the attached volume. `CREATE EXTENSION IF NOT EXISTS` is idempotent.

## 2. Storing embeddings (pgvector)

Keep embeddings in a **separate table**, 1:1 with provider, so the core schema and
Hibernate DDL for `service_providers` stay untouched and the feature is drop-in/drop-out.

```sql
-- N = embedding dimension of the chosen model (set once, must match the model):
--   e.g. Voyage voyage-3 = 1024, OpenAI text-embedding-3-small = 1536.
CREATE TABLE provider_embeddings (
    provider_id BIGINT PRIMARY KEY REFERENCES service_providers(provider_id) ON DELETE CASCADE,
    embedding   vector(1024) NOT NULL,
    model       VARCHAR(100) NOT NULL,
    updated_at  TIMESTAMP    NOT NULL DEFAULT now()
);
-- Approximate-NN index (cosine). Build after bulk load for speed:
CREATE INDEX provider_embeddings_hnsw
    ON provider_embeddings USING hnsw (embedding vector_cosine_ops);
```

**JPA/Hibernate mapping.** Spring Boot 3.2 ships Hibernate 6.4, which has the
`hibernate-vector` module. Add `org.hibernate.orm:hibernate-vector` and map a
`float[]`:
```java
@Entity
class ProviderEmbedding {
    @Id Long providerId;

    @JdbcTypeCode(SqlTypes.VECTOR)
    @Array(length = 1024)            // dimension
    float[] embedding;

    String model;
    Instant updatedAt;
}
```
Nearest-neighbour search is a native query using pgvector operators
(`<=>` cosine, `<->` L2, `<#>` inner product):
```sql
SELECT provider_id
FROM provider_embeddings
ORDER BY embedding <=> :queryVec
LIMIT :k;
```
Embeddings would be generated by an external model (e.g. Voyage AI, recommended by
Anthropic, since the Claude API itself has no embeddings endpoint) and written on
provider create/update.

**Reversibility:** `DROP TABLE provider_embeddings;` and remove the dependency — the
rest of the app is unaffected because nothing else references it.

## 3. Radius search: Haversine → PostGIS `ST_DWithin`

Today `LocationService` (`backend/.../service/LocationService.java`) does radius search in
Java: a bounding-box pre-filter (`getBoundingBox`) to narrow candidates, then the
Haversine `calculateDistance` / `isWithinRadius` to refine. Coordinates live on
`service_providers.base_latitude` / `base_longitude` (`numeric`). This is correct but
runs distance math in the app and can't use a spatial index.

PostGIS `ST_DWithin` replaces both the bounding-box trick and the Java refine with a
single index-backed SQL predicate. Outline (not to be done now):

1. Add a geography column derived from the existing lat/lon (kept in sync, or generated):
   ```sql
   ALTER TABLE service_providers ADD COLUMN base_geog geography(Point, 4326);
   UPDATE service_providers
      SET base_geog = ST_SetSRID(ST_MakePoint(base_longitude, base_latitude), 4326)::geography
    WHERE base_latitude IS NOT NULL AND base_longitude IS NOT NULL;
   CREATE INDEX service_providers_geog_gix ON service_providers USING gist (base_geog);
   ```
2. Query within radius (`ST_DWithin` on `geography` uses **metres**):
   ```sql
   SELECT * FROM service_providers
   WHERE ST_DWithin(base_geog, ST_MakePoint(:lon, :lat)::geography, :radiusMeters);
   ```
3. In Java, swap the `getBoundingBox` + Haversine path for this query (via a native
   query or a Hibernate Spatial mapping). Keep `LocationService.calculateDistance` for
   display ("X km away"), or use `ST_Distance`.
4. Backfill `base_geog` on write (trigger, generated column, or in the service layer).

**Reversibility:** the lat/lon columns and `LocationService` stay in place throughout, so
PostGIS is purely additive — `DROP COLUMN base_geog` + `DROP EXTENSION postgis` reverts
to the current Java Haversine behaviour with no data loss.

> No-PostGIS alternative: the `cube` + `earthdistance` extensions (already available
> locally) provide `earth_box`/`<@>` radius filtering with a GiST index, without the
> PostGIS dependency. Less capable than PostGIS but enough for simple radius queries.

---

## Summary

- **pgvector**: developable locally now; on Railway use the pgvector or Supabase image.
  Add `provider_embeddings` (separate table) + `hibernate-vector`. Fully drop-out.
- **PostGIS**: needs a PostGIS-enabled image locally and on Railway. Additive `base_geog`
  column + `ST_DWithin`; Haversine remains as fallback. Fully reversible.
- Both are isolated from the current schema — adopt independently when the AI/geo work
  is scheduled.
